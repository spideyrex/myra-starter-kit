Myra Starter Kit Documentation v2.0

A production-ready starter kit built on Laravel + Inertia.js + Vue 3 (TypeScript) with shadcn-vue components. Schema-driven forms, reusable UI components, CMS with articles and pages, configurable marketing homepage, and Artisan scaffolding for rapid admin panel development.

Key Features

  • Schema-Driven Forms — Define forms with a fluent TypeScript API instead of verbose templates
  • Schema-Driven Tables — Declarative column definitions with auto-rendering (badges, dates, booleans, images)
  • Artisan Scaffolding — Generate full CRUD resources or single pages with one command
  • Notification System — In-app notifications with bell dropdown, detail dialogs, preferences, and admin management
  • Authentication — Login, registration, password reset, email verification, and two-factor authentication
  • Role-Based Access Control — Spatie permissions with usePermissions composable for frontend checks
  • CMS (Content Management) — Articles with rich text editor, categories, and static pages with SEO fields
  • Homepage Builder — Settings-driven marketing landing page with hero, features, testimonials, pricing, and CTA sections
  • Built-in Admin Modules — Users, roles, settings, email logs, backups, API tokens, system health, activity log, media manager
  • AI Assistant — Bring-your-own-key AI integration (OpenAI, Anthropic, OpenRouter, or self-hosted Ollama) with a streaming writing assistant built into the rich text editor
  • Theme Selector — 10 predefined shadcn color themes (Zinc, Slate, Stone, Red, Rose, Orange, Green, Blue, Violet, Yellow) configurable from admin
  • Dark Mode — Full dark/light theme support with persistent user preference
  • Security — Profile security page with 2FA setup, password change, and browser session management
  • Command Palette — Ctrl+K fuzzy search for quick navigation across all admin pages

⚡ Quick Start
Create a new project with composer create-project myra/starter-kit my-project. Then scaffold new admin modules with php artisan myra:resource ModelName. See Installation and Getting Started.

Installation

Myra Starter Kit is installed via Composer's create-project command. All files are included in your project so you own the code and can customize everything.

Requirements

  • PHP 8.2+
  • Laravel 11 or 12 (fresh installation recommended)
  • Node.js 18+
  • A database (MySQL, PostgreSQL, or SQLite)

Step 1: Clone & Install Dependencies

Everything needed is committed to the repository — it installs with no private access or tokens.

git clone https://github.com/spideyrex/myra-starter-kit.git my-app
cd my-app

composer install
npm install

Step 2: Configure Your Database

Update your .env file with your database credentials:

# MySQL / PostgreSQL
DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=myra
DB_USERNAME=root
DB_PASSWORD=

# Or use SQLite for a quick start (no config needed)
DB_CONNECTION=sqlite

Step 3: Run the Installer

php artisan app:install

The install command handles the following automatically:

StepWhat it does
DatabaseRuns migrations and seeds roles, permissions, settings, and email templates
Admin userPrompts you to create a super-admin user (interactive mode)
EnvironmentValidates required .env variables
⚠ Non-Interactive Mode
If the interactive admin user prompt fails (e.g. in CI or non-interactive terminals), you can create the admin user manually via Tinker: 
php artisan tinker --execute="
\$user = \App\Models\User::create([
    'name' => 'Admin',
    'email' => 'admin@example.com',
    'password' => bcrypt('password'),
    'status' => 'active',
    'email_verified_at' => now(),
]);
\$user->assignRole('super-admin');
"

Step 4: Install Frontend Dependencies

npm install

Step 5: Build Frontend Assets

npm run build

Step 6: Start the Dev Server

composer dev

This starts the Laravel server, queue worker, log watcher, and Vite dev server concurrently. Or run them separately:

# Terminal 1
php artisan serve

# Terminal 2
npm run dev

Step 7: Log In

Visit http://localhost:8000 and sign in with your admin credentials. You'll land on the admin dashboard with all modules ready to use.

Re-running the Installer

The app:install command takes no flags. It is safe to re-run — if the application is already installed (the settings table has data) it asks for confirmation before continuing, and all seeders use firstOrCreate / updateOrInsert so existing data is preserved.

# Re-run setup (prompts for confirmation if already installed)
php artisan app:install
⚡ Starter Kit Pattern
Myra follows the same pattern as Laravel Breeze — all files are included in your project. You own the code and can modify anything. The myra/framework package provides the scaffold commands (myra:resource, myra:page).

Getting Started

Creating a New CRUD Resource

The fastest way to add a new admin module is the scaffold command:

php artisan myra:resource Product

This generates 5 files:

FilePurpose
app/Http/Controllers/Admin/ProductController.phpCRUD controller with injected service
app/Services/ProductService.phpService with search, create, update, delete
resources/js/Pages/Admin/Products/Index.vueList page with DataTable
resources/js/Pages/Admin/Products/Create.vueCreate form with FormFields
resources/js/Pages/Admin/Products/Edit.vueEdit form with pre-filled data

The command also prints route definitions to paste into routes/web.php:

// Products
Route::get('/products', [ProductController::class, 'index'])->middleware('permission:products.view')->name('products.index');
Route::get('/products/create', [ProductController::class, 'create'])->middleware('permission:products.create')->name('products.create');
Route::post('/products', [ProductController::class, 'store'])->middleware('permission:products.create')->name('products.store');
Route::get('/products/{product}/edit', [ProductController::class, 'edit'])->middleware('permission:products.edit')->name('products.edit');
Route::put('/products/{product}', [ProductController::class, 'update'])->middleware('permission:products.edit')->name('products.update');
Route::delete('/products/{product}', [ProductController::class, 'destroy'])->middleware('permission:products.delete')->name('products.destroy');

After Scaffolding

1. Add the routes

Paste the printed route snippet into routes/web.php inside your admin route group.

2. Create the model (if needed)

php artisan make:model Product -m

3. Customize the form schema

Open the generated Create/Edit pages and modify the schema:

const schema = [
    TextInput.make('name').required(),
    TextInput.make('sku').required().placeholder('PRD-001'),
    TextInput.make('price').numeric().required(),
    Textarea.make('description').colSpan(2),
    Select.make('category').options({
        electronics: 'Electronics',
        clothing: 'Clothing',
        books: 'Books',
    }),
    Toggle.make('is_active').label('Active'),
];

4. Update the controller validation

$validated = $request->validate([
    'name' => 'required|string|max:255',
    'sku' => 'required|string|unique:products,sku',
    'price' => 'required|numeric|min:0',
    'description' => 'nullable|string',
    'category' => 'required|in:electronics,clothing,books',
    'is_active' => 'boolean',
]);

5. Update the service

public function list(Request $request): LengthAwarePaginator
{
    return $this->applySearchAndPaginate(
        Product::query()
            ->when($request->category, fn ($q, $cat) => $q->where('category', $cat)),
        $request,
        searchable: ['name', 'sku', 'description'],
    );
}

6. Customize the Index page columns

Use the Table Builder API for declarative column definitions:

import { TextColumn, BadgeColumn, DateColumn, BooleanColumn } from '@/composables/useTableSchema';
import { EditAction, DeleteAction } from '@/composables/useTableActions';

const columns = [
    TextColumn.make('name').sortable().searchable(),
    TextColumn.make('sku').sortable(),
    TextColumn.make('price').sortable().money('USD'),
    TextColumn.make('category'),
    BooleanColumn.make('is_active').label('Active'),
    DateColumn.make('created_at').sortable(),
];

const actions = [
    EditAction.make('admin.products.edit'),
    DeleteAction.make('admin.products.destroy'),
];
<DataTable :columns="columns" :data="products" :actions="actions" route-name="admin.products.index" />

No template slots needed — columns auto-render based on type.

⚡ Schema vs Manual Slots
You can always override auto-rendering by providing a #cell-{key} slot. The schema builder is a convenience — slots still work when you need full control over a cell's output.

Form Builder API

The form builder provides a fluent API for defining form fields as TypeScript objects instead of verbose template markup.

Quick Comparison

Before (template-heavy):

<FormField label="Name" name="name" v-model="form.name" required :error="form.errors.name" />
<FormField label="Email" name="email" v-model="form.email" type="email" required :error="form.errors.email" />
<FormField label="Password" name="password" v-model="form.password" type="password" :error="form.errors.password" />
<FormField label="Role" name="role" v-model="form.role" type="select" :options="[...]" :error="form.errors.role" />

After (schema-driven):

const schema = [
    TextInput.make('name').required(),
    TextInput.make('email').email().required(),
    TextInput.make('password').password(),
    Select.make('role').options([...]),
];
<FormFields :schema="schema" :form="form" />

ℹ Accessibility
CodeMirror's contenteditable is not a labelable element, so the field passes role="textbox", aria-multiline, aria-labelledby="{fieldId}-label", aria-describedby and aria-invalid directly onto the editable node. // Controller
public function index(Request $request): Response
{
    $users = User::query()
        ->when($request->search, fn ($q, $s) => $q->where('name', 'like', "%{$s}%"))
        ->when($request->status, fn ($q, $v) => $q->where('status', $v))
        ->when($request->email_verified, function ($q, $v) {
            $v === '1' ? $q->whereNotNull('email_verified_at') : $q->whereNull('email_verified_at');
        })
        ->paginate(15)->withQueryString();

    return Inertia::render('Admin/Users/Index', [
        'users' => UserResource::collection($users),
        'filters' => $request->only(['search', 'status', 'email_verified']),
    ]);
}

⚠ Whitelists, not blacklists

public function reorder(Request $request): RedirectResponse

    $ids = $request->validate(['ids' => 'required|array'])['ids'];

Wizard Per-Step Validation

The WizardStep class supports per-step validation that blocks advancing to the next step until all required fields are filled and custom validators pass.

Basic Usage

Add .validate() to any wizard step with a map of field names to validation rules:

import { Wizard, WizardStep, TextInput, type ValidationRule } from '@/composables/useFormSchema';

const emailValidator: ValidationRule = (value) => {
    if (!value) return true; // handled by required
    const re = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    return re.test(value) ? true : 'Please enter a valid email address';
};

const schema = [
    Wizard.make([
        WizardStep.make('Personal Info')
            .schema([
                TextInput.make('first_name').required(),
                TextInput.make('email').email().required(),
            ])
            .validate({
                email: [emailValidator],
            }),
        WizardStep.make('Review')
            .schema([
                Textarea.make('bio'),
            ]),
    ]),
];

Validation Rules

A ValidationRule is a function that receives (value, form) and returns either true (valid) or an error message string:

type ValidationRule = (value: any, form: Record<string, any>) => string | true;

How It Works

  • Required fields are checked automatically (empty string, null, undefined, empty array)
  • Custom validators from .validate() run after required checks
  • Errors are written to form.errors and displayed below each field
  • An error summary appears above the step content when validation fails
  • The Next button only advances if all validations pass

File: resources/js/composables/useResourceForm.ts

import { useResourceForm } from '@/composables/useResourceForm';

Signature

function useResourceForm<T extends Record<string, any>>(
    options: ResourceFormOptions<T>
): { form: InertiaForm<T>; submit: () => Promise<void> }

Usage

// Create
const { form, submit } = useResourceForm({
    data: { name: '', email: '' },
    storeRoute: 'admin.users.store',
    confirm: { title: 'Create User', confirmText: 'Create' },
});

// Update
const { form, submit } = useResourceForm({
    data: { name: props.user.name, email: props.user.email },
    updateRoute: 'admin.users.update',
    updateRouteParams: props.user.id,

NotificationBell Component

The bell lives in the AuthenticatedLayout header and provides a quick-access popover for recent notifications. See Component Reference for full props/features.

How It Works

  1. Badge Count — Reads unreadNotificationsCount from Inertia shared props. Shows animated ping badge when > 0.
  2. Popover List — Displays up to 10 recent notifications with type-specific icons and unread indicators.
  3. Click to View — Clicking any notification closes the popover and opens a NotificationDetailDialog with full content.
  4. Mark All Read — Button at top of popover sends POST /notifications/mark-all-read.
  5. View All — Link at bottom navigates to /notifications full page.

Backend Setup (HandleInertiaRequests)

Share notification data in your middleware:

// app/Http/Middleware/HandleInertiaRequests.php
public function share(Request $request): array
{
    return [
        ...parent::share($request),
        'auth' => ['user' => $request->user() ? $request->user()->only(...) : null],
        'unreadNotificationsCount' => $request->user()?->unreadNotifications()->count() ?? 0,
        'recentNotifications' => $request->user()
            ?->notifications()
            ->latest()
            ->take(10)
            ->get() ?? [],
    ];
}

Each notification type has three channel toggles: Email, In-App (database), and Push. The Push toggle controls whether the user receives Firebase Cloud Messaging push notifications for that type.

Notification preferences with Email, In-App, and Push toggles per notification type

Database Schema

Schema::create('notification_preferences', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained()->cascadeOnDelete();
    $table->string('type');                  // system, user_action, security_alert
    $table->boolean('email')->default(true);
    $table->boolean('database')->default(true);
    $table->boolean('push')->default(true);  // Push notification preference
    $table->timestamps();
    $table->unique(['user_id', 'type']);
});

Backend Controller

// NotificationPreferenceController@update
$validated = $request->validate([
    'preferences' => 'required|array',
    'preferences.*.type' => 'required|in:system,user_action,security_alert',
    'preferences.*.email' => 'boolean',
    'preferences.*.database' => 'boolean',
    'preferences.*.push' => 'boolean',
]);

foreach ($validated['preferences'] as $pref) {
    DB::table('notification_preferences')->updateOrInsert(
        ['user_id' => $request->user()->id, 'type' => $pref['type']],
        ['email' => $pref['email'] ?? true, 'database' => $pref['database'] ?? true, 'push' => $pref['push'] ?? true]
    );
}

// AdminNotificationController@store
$notification = match ($validated['type']) {
    'system' => new SystemNotification(
        title: $validated['title'],
        message: $validated['message'],
        actionUrl: $validated['action_url'] ?? '',
    ),

$notification->sendPush = $request->boolean('send_push');

$recipients = $validated['target'] === 'all'

Adding Push to Notification Classes

Push is opt-in per notification. All four notification classes (SystemNotification, UserActionNotification, SecurityAlertNotification, BroadcastableNotification) support push:

class SystemNotification extends Notification
{
    public bool $sendPush = false;

    public function via(object $notifiable): array
    {
        $channels = ['database'];
        if ($this->sendPush && app(FirebaseService::class)->isEnabled()) {
            $channels[] = FcmChannel::class;
        }
        return $channels;
    }

    public function toFcm(object $notifiable): array
    {
        return [
            'title' => $this->title,
            'message' => $this->message,
            'action_url' => $this->actionUrl,
            'type' => 'system',
        ];
    }
}

RBAC — Shield Layer

Permissions follow a strict {module}.{ability} convention, declared once in config/shield.php and materialised by php artisan shield:generate. The super-admin role bypasses all checks via the Gate::before callback in AppServiceProvider; the admin role receives every generated permission.

// config/shield.php
return [
    'super_admin_role' => 'super-admin',
    'admin_role' => 'admin',
    'privileged_roles' => ['super-admin', 'admin'], // assignable only by a super-admin
    'modules' => [
        'users' => ['view', 'create', 'edit', 'delete'],
        // …
        'demo' => ['view'],
        'search' => ['view'],
        /* myra:modules */ // scaffolding commands append here
    ],
];

Convention middleware (shield)

The shield alias (App\Http\Middleware\ShieldPermission) derives the required permission from the route name: admin.{prefix}.index → {prefix}.view, create/store → create, edit/update → edit, destroy/force-delete/bulk-action → delete (anything else → view). It's intended for scaffolded pages whose route prefix matches their module; modules whose route name differs from the permission prefix (e.g. email-templates → email) keep their explicit permission: gate.

The previously open /admin/demo/* and /admin/search routes are now gated by demo.view and search.view.

Per-User Data Isolation

The App\Models\Traits\OwnedByUser trait stamps an owner column (created_by) on create and adds an owned global scope: authenticated non-super-admins see only their own rows, super-admins see everything, and unauthenticated requests are unaffected (so the public blog still works).

ModelIsolation
Article, Page, CategoryOwnedByUser global scope on created_by
MediaManager scoped to the uploader (media attached to the user); deletes ownership-checked
Users, Email TemplatesQuery-level scoping (a global scope here would break auth/session and system email lookups)
⚠ Public views & legacy rows
Public controllers (PublicArticleController, PublicPageController) call withoutGlobalScope('owned') so logged-in non-super users still see the full public site. Rows created before this feature have created_by = null and are visible only to super-admins until backfilled.

Role & User Protections

  • Non-super-admins never see or manage super-admin accounts; an admin cannot manage another admin.
  • Non-super-admins only see/manage users they created.
  • Only a super-admin can assign the privileged roles (admin, super-admin); other roles are filtered out of the assignment dropdown server-side.
  • Roles carry is_active and visible flags (custom App\Models\Role). A super-admin toggles them from Roles & Permissions: a disabled role cannot be assigned (rejected server-side); a hidden role is removed from non-super-admin pickers and lists. The super-admin role is locked (always active & visible).

<?php

namespace App\Http\Controllers\Admin;

use App\Http\Controllers\Controller;
use App\Models\Product;
use App\Services\ProductService;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;
use Inertia\Inertia;
use Inertia\Response;

class ProductController extends Controller
{
    public function __construct(private readonly ProductService $productService) {}

    public function index(Request $request): Response
    {
        return Inertia::render('Admin/Products/Index', [
            'products' => $this->productService->list($request),
            'filters' => $request->only(['search', 'sort', 'direction']),
        ]);
    }

    public function create(): Response
    {
        return Inertia::render('Admin/Products/Create');
    }

    public function store(Request $request): RedirectResponse
    {
        $validated = $request->validate([
            'name' => 'required|string|max:255',
        ]);

        $this->productService->create($validated);

        return redirect()->route('admin.products.index')
            ->with('success', 'Product created successfully.');
    }

    public function edit(Product $product): Response
    {
        return Inertia::render('Admin/Products/Edit', [
            'product' => $product,
        ]);
    }

    public function update(Request $request, Product $product): RedirectResponse
    {
        $validated = $request->validate([
            'name' => 'required|string|max:255',
        ]);

        $this->productService->update($product, $validated);

        return redirect()->route('admin.products.index')
            ->with('success', 'Product updated successfully.');
    }

    public function destroy(Product $product): RedirectResponse
    {
        $this->productService->delete($product);

        return redirect()->route('admin.products.index')
            ->with('success', 'Product deleted successfully.');
    }
}

Key Conventions

  • Constructor injection for services (private readonly)
  • Return Inertia::render() for page responses
  • Return redirect()->route()->with('success', ...) for mutations

$defaultSortstring'created_at'Default sort column
$defaultDirstring'desc'Default sort direction
$perPageint15Items per page

How It Works

  1. Search: If $request->search exists and $searchable is not empty, applies WHERE (col1 LIKE %search% OR col2 LIKE %search% OR ...)
  2. Sort: If $request->sort exists, applies ORDER BY {sort} {direction}. Otherwise uses defaults.
  3. Paginate: Calls ->paginate($perPage)->withQueryString() to preserve query params in pagination links

// app/Http/Middleware/HandleInertiaRequests.php
public function share(Request $request): array
{
    return [
        ...parent::share($request),
        'auth' => [
            'user' => $request->user() ? [
                ...$request->user()->only('id', 'name', 'email', 'avatar', 'status'),
                'roles' => $request->user()->getRoleNames(),
                'permissions' => $request->user()->getAllPermissions()->pluck('name'),
            ] : null,
        ],
        'flash' => [
            'success' => fn () => $request->session()->get('success'),
            'error' => fn () => $request->session()->get('error'),
            'warning' => fn () => $request->session()->get('warning'),
            'info' => fn () => $request->session()->get('info'),
            'newToken' => fn () => $request->session()->get('newToken'),
        ],
        'unreadNotificationsCount' => fn () => $request->user()?->unreadNotifications()->count() ?? 0,
        'recentNotifications' => fn () => $request->user()
            ?->notifications()->latest()->take(5)->get() ?? [],
        'impersonating' => fn () => $request->session()->has('impersonator_id'),
        'currentTeam' => fn () => $request->user()?->currentTeam,
        'teams' => fn () => $request->user()?->teams()->get() ?? [],
        // Cached for 1 hour; 'site_settings_shared' is cleared when settings are saved
        'siteSettings' => fn () => cache()->remember('site_settings_shared', 3600, fn () => [...]),
        'aiEnabled' => fn () => cache()->remember('ai_enabled', 3600, fn () => app(AiSettings::class)->enabled),
        'firebaseConfig' => fn () => cache()->remember('firebase_web_config', 3600, fn () => [...]),
    ];
}

Plugin System v2.4

A plugin is one class extending one abstract with one required method that returns a Manifest. Everything the plugin contributes — permissions, reports, imports, routes, policies, commands, migrations, translations and sidebar items — is declared once, in that manifest. There is no package service provider and no per-panel registration call.

Writing a plugin

namespace App\Plugins\Billing;

use App\Admin\Plugin\Manifest;
use App\Admin\Plugin\MyraPlugin;

class BillingPlugin extends MyraPlugin
{
    public static function id(): string
    {
        return 'billing';
    }

    public function manifest(Manifest $manifest): Manifest
    {
        return $manifest
            ->requires('2.4.0')
            ->permissions(['billing' => ['view', 'edit']])
            ->reports(['invoices' => InvoicesReport::class])
            ->routes(fn () => Route::get('/billing', InvoicesController::class)
                ->middleware('permission:billing.view')->name('billing.index'));
    }
}

Registration is explicit

Plugins are listed by class in config('myra.extensions.plugins'). There is deliberately no composer auto-discovery: a plugin registers routes inside the admin middleware stack and merges entries into config('shield.modules'), so installing a package must never be enough on its own to grant either.

'extensions' => [
    'strict'  => env('MYRA_PLUGINS_STRICT', null),
    'plugins' => [
        \App\Plugins\Example\ExamplePlugin::class,
        // myra:plugins — make:myra-plugin inserts classes above this line.
    ],
],
ℹ A failing plugin never takes down the admin
PluginRegistry::load() catches per plugin, records the exception in failed(), reports it, and carries on. myra.extensions.strict rethrows instead; null means strict in local and testing, quarantined in production. The demo page at /admin/demo/plugins lists both the loaded plugins and the quarantined ones with their exception message.

Clusters, Server Navigation, Nested & Singular Resources v2.4

A cluster groups related resources under one collapsible sidebar entry and, optionally, one URL segment. Cluster membership merges from both directions: a cluster can enumerate its children, and a resource can declare its cluster.

The sidebar addition is additive by construction

The hardcoded navigation groups in AuthenticatedLayout.vue stay byte-identical. A new myraNav Inertia prop carries server contributions and serialises as [] when nothing is registered, so merging it is the identity operation. tests/js/navIdentity.spec.ts asserts that myraNav: [] renders exactly the same list as the prop being absent entirely.

// App\Admin\Navigation
NavItem::make('clusters.learning.courses')
    ->route('admin.learning.courses.index')
    ->icon('BookOpen')
    ->permission('demo.view');
ℹ Filtered twice, on purpose
Permissions are filtered on the server in NavRegistry::forUser() and again on the client with can(). A server bug can therefore narrow visibility but never widen it. A parent with no surviving children is dropped entirely — an empty expander never renders. Icons cross the wire as strings resolved through an explicit allowlist; an unknown name degrades to LayoutGrid.

Nested resources

ParentResource + ResolvesParentResource. Implicit route binding ignores global scopes, so the parent is re-queried through its own scopes after binding: an out-of-scope parent becomes a 404, never a readable id. Generated nested routes carry ->scopeBindings(), so /admin/courses/1/lessons/9 404s when lesson 9 belongs to another course — with no controller code and an indexed two-column lookup.

Singular resources

SingularResource + HandlesSingularRecord for one-row settings pages. Exactly two routes are ever generated: GET /admin/{key} and PUT /admin/{key}. No create, no destroy, no {record} parameter. The first PUT creates the row; every later one updates the same row.

Multi-Tenancy v2.4

⚠ Opt-in, default off
With myra.tenancy.enabled false, nothing is registered: no global scope, no creating hook, no validation-rule change, no middleware, no Inertia prop. bootBelongsToTenant() returns before addGlobalScope and before static::creating — a registered scope that returns early still mutates the builder and still appears in getGlobalScopes(), which is not good enough for a data-visibility feature.

Two independent locks

Scoping requires config('myra.tenancy.enabled') === true and the model class listed in config('myra.tenancy.models'). Adding the trait to a model is not sufficient, so a merge that adds a trait can never change production visibility on its own.

'tenancy' => [
    'enabled'            => env('MYRA_TENANCY', false),
    'model'              => \App\Models\Team::class,
    'column'             => 'team_id',
    'null_rows'          => 'strict',   // 'strict' | 'shared'
    'super_admin_bypass' => true,
    'models'             => [],
],

Fail closed

With scoping active and no tenant resolved, the scope applies 1 = 0 — zero rows, not every row. Legacy rows with a NULL tenant column are invisible to non-super-admins under null_rows: 'strict'. The 'shared' mode wraps its orWhereNull in a nested closure; an unwrapped one leaks the whole table.

API

CallEffect
Tenancy::apply($query, $table)The single predicate, for query sites that do not go through Eloquent scopes. A literal no-op when disabled.
Tenancy::for($tenant, $callback)The only way to change tenant. Restores in a finally, including on exception. There is no bare setter.
Tenancy::without($callback)Audited escape hatch; logs to the activity log when tenancy is enabled.
Tenancy::unique() / exists()Validation rules that do not leak across tenants, degrading to the plain rules when disabled.

The tenant is resolved lazily from users.current_team_id with membership re-validated on every request — never from a route or query parameter. There is no tenancy middleware and no route change.

Proving the disabled path

myra:tenancy-baseline writes the SQL and bindings for canonical queries as guest, member and super-admin. tests/Feature/Tenancy/DisabledPathIsNoOpTest asserts the live queries still match that baseline byte for byte, and that no tenant scope and no extra creating listener exists. myra:tenancy-audit refuses readiness while any NULL tenant row remains, turning a silent visibility change into a blocked deploy.

Scale & Testing Helpers v2.4

Cursor pagination is a sibling, never a replacement

applySearchAndPaginate() keeps its exact signature and behaviour — saved views, deep links and meta.links all depend on length-aware pagination. applySearchAndCursorPaginate() shares the same sort whitelist and per-page clamp and adds no OFFSET and no COUNT(*).

ℹ The primary-key tiebreak
The cursor path always appends orderBy(id). Without it, cursor pagination silently skips or repeats rows whenever the sort column is not unique. On the length-aware path the same tiebreak is optional and off by default (myra.performance.stable_sort), because turning it on changes the SQL of every existing admin table.

meta.mode is stamped only on cursor responses. An absent mode means length-aware, so every existing controller response is byte-identical and no controller needed an edit.

Virtualised rows

useVirtualRows has zero dependencies and keeps the markup a real <table> with spacer rows, so <colgroup> widths, the sticky header and the column manager keep working. Rows are keyed by row.id, never by index — inline editing keys its optimistic value and its rollback the same way, and an index-recycling virtualiser would break all three. Virtualisation refuses, with a dev-only warning rather than a broken table, when groupBy, reorderable or an expanded-row slot is in play.

php artisan myra:scale-seed 100000
